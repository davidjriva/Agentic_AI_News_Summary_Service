Three approaches for /metrics

How the page gets its data and renders charts

A

Server-rendered (recommended)

FastAPI queries DB and RECIPIENTS at request time, passes all data as JSON into the Jinja2 template. Chart.js reads it from inline <script> tags. No client-side fetch, no extra endpoint.

Pros

  • Matches existing dashboard pattern exactly
  • Single request loads the full page
  • Simple — one new route + one new template

Cons

  • No standalone API to call from other tools
B

API + thin shell

GET /api/metrics returns JSON. GET /metrics is a bare HTML shell that fetch()es it on load and renders charts dynamically.

Pros

  • JSON endpoint is independently testable
  • Easy to call from scripts or other UIs

Cons

  • Extra moving part (two routes, fetch logic, loading state)
  • Diverges from how the rest of the server works
C

Hybrid — server-rendered + JSON endpoint

Add both GET /metrics (full HTML, data baked in) and GET /api/metrics (JSON only). The HTML page uses the same inline-data approach as Option A; the JSON endpoint is a bonus for tooling.

Pros

  • Best of both: fast page load + testable API

Cons

  • Two routes instead of one; slightly more code to maintain

My recommendation: A — keeps the codebase consistent, covers all the metrics you asked for, and adds zero complexity. A JSON endpoint can always be added later if needed.
