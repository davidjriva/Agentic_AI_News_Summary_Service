# Newsletter Subscriptions — Design

**Date:** 2026-06-29
**Status:** Approved (pending spec review)

## Context

Today the newsletter ships to a static list from `EMAIL_RECIPIENTS` (env, comma-separated), and the emailer sends a single message with every address in the `To:` header — so recipients would see each other's emails and there is no unsubscribe path. We need a real subscriber system: people subscribe from a form on the personal portfolio (a separate Next.js app), confirm via double opt-in, and can unsubscribe from any newsletter. Subscriber emails are PII and must be stored securely in the existing Supabase Postgres database.

## Architecture & responsibility split

This service runs **locally** (launchd-triggered) and is not publicly reachable, so it cannot host the public subscribe/confirm/unsubscribe endpoints. The portfolio is a publicly hosted Next.js app **with a backend**, so it owns the public request path and talks to Supabase directly with the `service_role` key.

- **This repo (newsletter service):**
  - Owns the `subscribers` **table schema** (SQLAlchemy model + Alembic migration, RLS-enabled with no policies).
  - Reworks the **emailer** to broadcast to confirmed subscribers, one personalized message each, with a per-subscriber unsubscribe link.
  - Never serves a public HTTP request for this feature.
- **Portfolio (separate repo):**
  - Owns the public routes (`subscribe`, `confirm`, `unsubscribe`), generates the tokens, and sends the **transactional** emails (subscription confirmation, unsubscribe confirmation) via its own email provider.
  - See `docs/portfolio-newsletter-integration.md` for the full handoff contract.

The split is clean: **portfolio = all action-triggered transactional mail + public routes; this service = the scheduled newsletter broadcast.**

## Data model — `subscribers`

| column | type | constraints / notes |
|---|---|---|
| `id` | bigint identity | primary key |
| `email` | text | **unique**, not null — the PII we protect |
| `status` | text | not null, default `'pending'`; one of `pending` / `confirmed` / `unsubscribed` |
| `confirm_token` | text | unique; double-opt-in capability token, consumed on confirm |
| `unsubscribe_token` | text | unique, not null; **stable**, embedded in every newsletter |
| `subscribed_at` | timestamptz | default `now()` |
| `confirmed_at` | timestamptz | null until confirmed |
| `unsubscribed_at` | timestamptz | null until unsubscribed |

- **Tokens** are URL-safe random, ≥32 bytes (`secrets.token_urlsafe(32)`), **generated by the portfolio** at insert time. This repo only ever *reads* `unsubscribe_token`.
- Rows are **never deleted** on unsubscribe (audit trail; supports CAN-SPAM honoring; prevents silent re-add). Re-subscribe flips an existing row back to `pending`.
- **RLS:** enabled, **zero policies** — identical to the other tables. Only the `service_role` (portfolio) and the table-owning `postgres` role (this service) can access it; the public `anon`/publishable key cannot read subscriber emails. **No RLS policy changes are needed elsewhere.**

## Data model — `newsletter_deliveries`

Per-issue send tracking (added after review): one row per `(run, subscriber)`.

| column | type | notes |
|---|---|---|
| `id` | bigint identity | primary key |
| `run_id` | text | not null; the newsletter run |
| `email` | text | not null; recipient at send time |
| `status` | text | not null; `sent` or `failed` |
| `error` | text | null; SMTP error on failure |
| `sent_at` | timestamptz | default `now()` |

`UNIQUE(run_id, email)` so recording is **idempotent** (a re-run upserts the row) — supports "who didn't get this issue → retry". RLS enabled, no policies, same as everything else.

**Decisions (from review):**
- **No batch-send.** Per-person unsubscribe requires one message per subscriber (personal token in body + `List-Unsubscribe` header), so we can't BCC. The emailer already does the only Gmail-scale optimization: one authenticated SMTP connection reused across the loop. Provider batch-with-substitution APIs are a future concern at thousands of subscribers.
- **Subscribe/unsubscribe history:** latest dates on the subscriber row only (no events table); resubscription overwrites them.

## This repo's changes

### `src/models.py`
Add a `Subscriber` declarative model matching the table above (`Text`, `BigInteger` identity PK, `timestamptz` with `server_default=func.now()` for `subscribed_at`).

### Alembic migration
Autogenerate the `subscribers` table, then hand-add `op.execute("ALTER TABLE public.subscribers ENABLE ROW LEVEL SECURITY")` (the autogenerate diff won't capture RLS), mirroring `ebfc671a4078_enable_row_level_security.py`.

### `src/emailer.py` (the core rework)
Replace the static-`RECIPIENTS`, single-`To:` send with per-subscriber delivery:

```
def send_newsletter(html, plain_text, run_time):
    subscribers = _confirmed_subscribers()   # [(email, unsubscribe_token), ...]
    if not subscribers: log "no confirmed subscribers"; return
    open one SMTP connection (login once)
    for email, token in subscribers:
        unsub_url = f"{PORTFOLIO_BASE_URL}/newsletter/unsubscribe?token={token}"
        per_html  = html.replace(UNSUB_PLACEHOLDER, unsub_url)
        per_plain = plain_text.replace(UNSUB_PLACEHOLDER, unsub_url)
        msg = MIMEMultipart("alternative")
        msg["Subject"], msg["From"] = subject, sender
        msg["To"] = email
        msg["List-Unsubscribe"] = f"<{unsub_url}>"
        msg["List-Unsubscribe-Post"] = "List-Unsubscribe=One-Click"
        msg.attach(plain); msg.attach(html)
        try: smtp.sendmail(sender, [email], msg.as_string())
        except SMTPException: log and continue   # failure isolation
```

- `_confirmed_subscribers()` queries `select(Subscriber.email, Subscriber.unsubscribe_token).where(Subscriber.status == "confirmed")` via `get_session()`.
- `send_newsletter(html, plain_text, run_time, run_id=None)` gains `run_id`; `main.py` passes it. After the send loop it upserts a `newsletter_deliveries` row per subscriber (`sent`/`failed` + error) keyed on `(run_id, email)`.
- **One message per subscriber** (each `To:` is a single address — no cross-recipient exposure) with that subscriber's unsubscribe URL.
- **`List-Unsubscribe` + `List-Unsubscribe-Post: One-Click`** headers so Gmail/Apple Mail show a native Unsubscribe button that POSTs.
- **Failure isolation:** a single bad address logs and is skipped; the batch continues. Reuse one authenticated SMTP connection for the whole batch (Gmail free tier allows ~500 recipients/day — ample).

### `src/renderer.py` / `templates/newsletter.html.jinja2`
Add an unsubscribe footer to both HTML and plain-text outputs containing a **literal sentinel** (`%%UNSUBSCRIBE_URL%%`, not a Jinja variable, so it survives rendering) that the emailer substitutes per recipient.

### `src/config.py`
- Add `PORTFOLIO_BASE_URL` (e.g. `https://<portfolio-domain>`), read from `.env`; used to build unsubscribe links. Document in `.env.example`.
- **Remove `EMAIL_RECIPIENTS` as the send source.** The `subscribers` table is the single source of truth, so every recipient has a real unsubscribe token. The owner receives the newsletter by being a `confirmed` subscriber (self-subscribe, or seed one row).

### `src/server.py` (metrics)
The `/metrics` route currently computes `subscribers = len(_cfg.RECIPIENTS)` and `emails_delivered = successful_runs * subscribers`. Since `RECIPIENTS` is being removed as the send source, replace this with a **count of `confirmed` subscribers** from the table (`select(func.count()).where(Subscriber.status == "confirmed")`). `emails_delivered` keeps its formula against that count.

## Error handling

- No confirmed subscribers → log and no-op (run still succeeds).
- SMTP per-recipient failure → log, skip, continue (don't abort the run or fail the pipeline).
- Missing `PORTFOLIO_BASE_URL` → fail fast at send time with a clear message (links would be broken otherwise).

## Testing

- **Model/migration** (testcontainers `db` fixture): `subscribers` table exists with expected columns; RLS enabled.
- **Emailer** (mock `smtplib.SMTP`, seed subscribers via ORM):
  - Only `status='confirmed'` rows receive mail; `pending`/`unsubscribed` are excluded.
  - Each message's `To:` is a single address and contains **that subscriber's** unsubscribe URL + `List-Unsubscribe` header.
  - A raised `SMTPException` for one recipient does not prevent the others from being sent (failure isolation).
  - Empty confirmed set → no SMTP login attempted, no error.
- The existing `tests/test_emailer.py` (which asserts the old static-`RECIPIENTS` single-`To:` behavior) is **rewritten** for the per-subscriber model. Any test asserting `len(_cfg.RECIPIENTS)` in metrics is updated to seed `confirmed` subscribers instead.

## Out of scope (this repo)

The public `subscribe` / `confirm` / `unsubscribe` routes, token generation, and the transactional confirmation/unsubscribe emails are all **portfolio** responsibilities — specified in `docs/portfolio-newsletter-integration.md`.
